title: Manage access and security
description: Set up staff access, protect source records and credentials, and understand which security boundaries need independent validation.
---

Access to a dashboard is not permission to approve payments. Assign each person the
access needed for their work and keep review duties separate.

## Before inviting staff

1. Configure working email delivery for verification and password recovery.
2. Create the first administrator with `app:bootstrap-admin` using a unique password.
3. Verify the email address and configure MFA.
4. Keep public registration and impersonation disabled unless explicitly reviewed.
5. Create staff access deliberately; public registration does not grant a staff role.

The ordinary app uses Fortify for authentication and Filament for panel authentication.
Payment reviewer enrollment is an additional requirement, not the same as signing in
with MFA.

## Who can do what?

The precise policy for each action is authoritative; do not infer access from a job title.
For example, current manual collection recording accepts verified finance officers,
admins, and super admins. Independent collection review requires an admin or super admin
who did not record that batch.

Normal payment review additionally requires directly assigned payment authorization
permission and independent enrollment of the reviewer's current authenticator. Being a
super admin does not satisfy every independent-review check.

Use [Review a payment](../payment-approvals/) for the staff process.

## Do not treat the bridge as independent approval

The bridge no longer chooses reviewers, grants permissions, generates TOTP inputs or
invokes payment approval actions. It is read-only. Historical synthetic review records
must be independently investigated, not promoted into fresh authorization.

See [Current limits](../../institution/safety-readiness/#read-only-bridge-and-assistance-boundaries)
before exposing payment-capable workflows to staff.

## Protect documents and personal data

Manual source uploads in Collections use private storage. Limit access to those who
need it; keep public download URLs, student records, and institution source documents
out of commits and support screenshots.

Keep personal information offchain. Public addresses and amounts can still be linkable.
Obtain separate approval for external AI processing and for publishing pilot recordings,
school names, logos, or quotes.

## AI boundaries

Advisory classifications, citations, and narratives are not spend permission. The
application has defensive envelopes and answer guards in specific paths, but not every
workflow uses the same guard or has the same side effects.

Provider failures should not be disguised as a confident result. Institution policy
publication and evaluation can require provider readiness; manual collection recording
and deterministic planning are separate.

Keys saved through AI Providers are encrypted with `APP_KEY` and not returned to the
edit form. Preserve that key with your backups. Encryption does not protect a secret
from a compromised running server that can decrypt it.

## Webhook ingestion

The Circle webhook endpoint is opt-in. It returns `404` unless enabled with a
developer-wallet driver, and then requires signature headers, raw-body verification,
an allowed subscription, supported type/network identity, and durable queue configuration.
Oversized or invalid input is rejected.

A verified notification is deduplicated and queues observation. It never creates a
payment authorization or proves matching settlement by itself. Keep webhook verification
and settlement verification as separate checks.

## Operational secrets and recovery

- Keep `.env`, provider sessions, API keys, and private keys out of version control.
- Never collect passwords, OTPs, or authenticator secrets in support logs.
- Treat shell access as privileged. Passing a staff ID to a command is attribution,
  not proof that this person logged in and approved it.
- Keep the application's encryption key stable. Rotating a leaked credential is not
  a reason to regenerate `APP_KEY` or erase finance history.
- Restore backups with new submission stopped. Reconcile unresolved attempts before
  permitting new payments.
