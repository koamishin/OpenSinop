---
title: Is OpenSinop right for our school?
description: What a school can evaluate now, what stays in its existing finance process, and what each institution must operate for itself.
---

OpenSinop is a self-hosted application for reviewing collections, checking proposed
department spending, and retaining the evidence behind finance decisions.

It is a reasonable project to **evaluate with simulated or approved test data**.
It is not currently a certified replacement for your accounting system or a ready-made
service for real institutional funds.

## A useful first problem

Start with one department asking:

> We have received these fees. Which already approved bills can we cover while keeping
> restricted money and reserves intact?

You can answer that using aggregate collections, existing bills, and the department's
approved budget. No new student portal, student wallet, AI provider, or bank integration
is needed for that starting point.

## What each institution runs

**One institution, one installation.** Each school needs its own database, private
files, application key, mail settings, background processes, and provider credentials.
Two unrelated schools should run two instances, even with the same IT operator.

The setup command persists one institution identity and refuses ambiguous data. This
is not shared hosting with complete tenant isolation.

## Who needs to be involved?

| Person | Responsibility |
| --- | --- |
| Finance owner | Choose the problem, source records, review process, and limits. |
| Finance officer or cashier | Capture receipt evidence and prepare the selected records. |
| Independent reviewer | Check sources and make authorized review decisions. |
| IT operator | Run the server, access controls, backups, mail, workers, and recovery. |
| Privacy owner | Approve data handling, external AI use, and any public pilot evidence. |

A single super admin account is not a replacement for independent staff review.
The experimental bridge is especially unsuitable as evidence that two people approved
a payment; [understand its limits](../safety-readiness/#read-only-bridge-and-assistance-boundaries).

## What remains outside OpenSinop?

Keep your official accounts, tax and payroll calculations, procurement authorization,
bank reconciliation, and actual supplier payment status in your institution's existing
systems unless a separate validated integration covers them.

Local-currency receipts are not automatically converted to USDC. A local reference
valuation is not an executable exchange quote. A testnet payment does not clear a
real school payable.

## How another school starts

1. Agree on one department, its finance owner, and a small set of permitted records.
2. Have IT create an isolated evaluation instance with simulated payments.
3. Set the school identity, verify staff email, and configure access and MFA.
4. Record a sample collection and have another person review it.
5. Plan a selected set of approved bills and compare the result with the usual process.
6. Review the outcome before expanding. Network payments are a separate testnet project,
   not an automatic next step after installation.

## Ownership, cost, and license

The code uses the MIT license. A school may use and adapt it while retaining required
notices. It runs its own infrastructure and owns its configuration and data.

Self-hosting does not make Circle, hosted AI, email, network access, or local compliance
free or available everywhere. The institution remains responsible for those services
and any applicable terms. The MIT license provides no financial warranty or support SLA.
