Run `php artisan <command> --help` for the current options. Commands are operator tools,
not a substitute for a staff login or independent human authorization. Supplying a user
ID records attribution; it does not prove the user personally approved that operation.

## Start with read-only inspection

```bash
php artisan lepton:doctor --skip-transfer
php artisan lepton:login --status
php artisan app:finance-preview --days=30 --no-interaction
```

The finance preview is read-only and does not reserve or execute payments. Doctor also
has transfer and wallet-adoption options; do not add those without separate authorization.

## Set up an institution

| Command | Purpose |
| --- | --- |
| `app:install` | Persist one institution and conservative settings. Use `--institution`, `--country`, `--timezone`, `--locale`, and `--currency`; existing identity needs reviewed `--adopt-institution` handling. |
| `app:bootstrap-admin` | Create the first super admin interactively with `--name` and `--email`. No password CLI option. |

Installation does not run migrations itself, provision wallets, seed finance fixtures,
or disable every runtime flag. Follow [Installation](../../getting-started/installation/)
instead of treating this table as a complete setup script.

## Prepare reviewed finance evidence

| Command | Purpose and important inputs |
| --- | --- |
| `app:prepare-finance-policy` | Create a version with exact reserve/limits. Inputs include version, `--actor`, `--reserve`, `--auto-limit`, `--daily-limit`, and `--max-fee`. |
| `app:activate-finance-policy` | Activate a version using a separate `--reviewer` and explicit `--expected-activation` context. Activation is not payment approval. |
| `app:draft-institution-policy` | Create a starting institution policy draft with author ID and optional `--save`. Not publication. |
| `app:prepare-vendor-payment` | Prepare an exact full-bill draft with invoice, actor, wallet, fee, and stable `--intent-key`. Not a send command. |

Use the browser workflows for staff review. Do not pass a convenient admin ID merely
to satisfy an action's required actor.

## Dispatch existing work

These commands can queue or process existing work; they are not all read-only.
The scheduler invokes them under individual runtime settings:

| Command | Work |
| --- | --- |
| `app:dispatch-finance-workflows` | Dispatch planning/review runs. |
| `app:dispatch-payment-submissions` | Dispatch payment submissions; includes stale-work recovery options. |
| `app:dispatch-student-tuition` | Dispatch tuition submission/observation work. |
| `app:dispatch-student-bill-payments` | Dispatch campus-bill payment work. |
| `app:dispatch-policy-evaluations` | Dispatch queued policy evaluations. `--sync` runs in the current process. |
| `app:dispatch-mandate-occurrences` | Check due mandate occurrences and record dispositions. Not proof of a payment. |
| `app:recover-circle-notifications` | Re-queue verified notifications awaiting observation. |

See [Operations](../../guides/operations/) for queues, connection selection, and runtime
defaults before running a dispatcher manually.

## Reconcile and retain evidence

| Command | Work |
| --- | --- |
| `app:reconcile-payment-submissions` | Match expected submitted payments against Arc evidence. `--mirror` additionally writes eligible local ledger records. |
| `app:reconcile-tuition-receipts` | Recover intake of eligible settled tuition movements. |
| `app:reconcile-student-bill-receipts` | Recover intake of eligible student bill movements. |
| `lepton:reconcile` | Legacy transaction receipt reconciliation; weaker than matching an expected bill. `--json`, `--limit`, and `--fix` are available. |

Legacy `--fix` marks readable chain-reverted rows failed, not absent hashes. Keep
unresolved outcomes for investigation. See
[Settlement verdicts](../../institution/safety-readiness/#settlement-verdicts).

## Payment-capable and provisioning commands

:::danger[These are not setup or health checks]
`eduflow:autonomous-pipeline-bridge`, `app:demo`, and direct `lepton:transfer` can invoke
money movement. The bridge command does not universally honor its scheduled enabled
flag. Do not run it as a diagnostic or to bypass normal review.

Student wallet creation consumes provider capacity, and funding uses an external
faucet. Neither is a harmless way to populate a dashboard.
:::

- `student:generate-wallet`: operator-controlled pilot wallet generation; inspect `--list` first.
- `student:fund-wallet`: explicit pilot funding; inspect `--help` and current provider limits.
- `app:demo`: legacy fixtures/cycle, documented only for simulated local use in [Local setup](../../getting-started/local-development/#about-appdemo).
- `eduflow:autonomous-pipeline-bridge`: read-only receipt review handoff; never submits funds. See [Current limits](../../institution/safety-readiness/#read-only-bridge-and-assistance-boundaries).

## Starter scaffolding commands

`setup:starter-kit` and `install:features` belong to starter/feature scaffolding, not
ordinary school operation. They can rewrite or consume scaffolding. Inspect them
before use; they are not recommended installation or recovery steps for a school.

## Assistance commentary

`app:dispatch-assistance-advice` recovers queued optional assistance commentary.
Requires approved provider disclosure, advisory enablement, institution context and
a database/Redis queue with `retry_after > 120`. It submits no payments and does not
reopen concluded or interrupted provider attempts automatically.
